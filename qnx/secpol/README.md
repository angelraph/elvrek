# Elvrek security policy

Two layers keep the advisor away from the piston and the shock line.

**Layer 1: works on any QNX 8.0 image, already in the code.**
- `elvrekd` attaches `/dev/elvrek/piston` and `/dev/elvrek/shock` as mode `0400`, root-owned. The resource manager's default open handler checks permissions, and the write handler returns `EPERM` for these devices in any case.
- `/dev/elvrek/operator` is `0600` root. `/dev/elvrek/advice` is `0622`, so the advisor can only write advice.
- `/elvrek_hw` shared memory is `0600` root. The advisor maps only `/elvrek_ecg`, and only read-only.
- `elv-advisor` drops to uid 2002, then denies and locks `PRIORITY`, `SPAWN`, `FORK`, `SETUID`, `MEM_PHYS` and `IO` with `procmgr_ability()`.
- `elvrekd` denies and locks `SPAWN`, `FORK`, `SETUID`, `SETGID`, `MEM_PHYS`, `IO` and `INTERRUPT` after start-up.
- Proof on the target: `elv-advisor -a` tries every forbidden path and prints the refusals (fault suite case T3).

**Layer 2: kernel security policy (secpol), enforcing image.** Every process runs under its own type and is denied by default.

- `elv_plant_t`: launched as `on -T elv_plant_t elv-plant`. May connect to nothing. Abilities: `priority` up to 55.
- `elvrekd_t`: launched as `on -T elvrekd_t elvrekd`. May connect to its own channels. Abilities: `priority` up to 60, `pathspace` (register `/dev/elvrek/*`).
- `elv_super_t`: launched as `on -T elv_super_t elv-super`. May connect to `elvrekd_t` (status read). Abilities: `spawn` the advisor only.
- `elv_advisor_t`: launched as spawned by elv-super. May connect to `elvrekd_t` (advice write). Abilities: none (no priority above 10, no spawn, no setuid).
- `elv_telem_t`: launched as `on -T elv_telem_t elv-telemetry`. May connect to `elvrekd_t` (status read). Abilities: network.
- `elv_ctl_t`: launched as crew shell. May connect to `elvrekd_t`. Abilities: none.

**How it's produced (at the kill gate, on the target):**
1. Build the image with secpol in development (permissive) mode.
2. Run `secpolgenerate` while the fault suite exercises every process, including restarts.
3. Hand-tighten the result so that `elv_advisor_t` has no ability and reaches only the advice path. Commit it here as `elvrek.pol`.
4. Rebuild with the policy enforced and rerun the fault suite. Case T3 must still pass, and it must also pass when the advisor runs as root under its type. That second run is the test that only the kernel policy, not file modes, can pass.

The exact `.pol` syntax is generated by the SDP tools rather than hand-written here. That way the committed file is guaranteed to compile with `secpolcompile`.
