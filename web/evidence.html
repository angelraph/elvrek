57 records from two public PhysioNet databases. The check measures five things on 0.8 s of clean ECG, including how much of the signal sits in the 3 to 9 Hz fibrillation band. Reading the rhythm through the compressions

Every defibrillator stops compressions to read the heart, because compressions bury the ECG. Elvrek is the machine pushing, so it knows the phase of every stroke and subtracts its own artifact. On real arrest ECG from PhysioNet, at 0 dB, compared with always pausing to look: VF shocked at the check 82.1% against 75.0%, wrong shock advice for sinus 0.7% against 2.3%, and 70% of sinus checks with no pause at all. When the reading is not sure, the 0.8 s look runs as before. The thresholds were set on one database and scored on another, which we had to look at twice; the full method and that disclosure are in the repository (docs/ZERO-PAUSE.md).

Compressing before the system has booted

The safety process and the hardware stand-in live in the QNX boot image and start from the first boot script, before the disks are mounted or the network is up. Over five boots each on QNX 8.0 in QEMU, the first full compression came 1.39 s after the kernel started (median), against 3.67 s when the same programs started after the normal boot like an ordinary application. The piston was already working while the rest of the system came up, and every boot ended compressing with no fault. These are emulator times; on a real board the firmware adds its own time before the kernel runs.

The crew console, on QNX Screen

The crew sees one screen, drawn on the QNX target with QNX Screen: rate, depth and peak force, the countdown to the next rhythm check and what the reading through the compressions says, the charger, the EtCO2 trend and the compression fraction. It only reads the safety process's status, so it cannot move the piston or fire a shock, and if it hangs nothing else notices. In a recorded run the crew saw charging while compressing, then shock delivered: the shock window lasted 3 ms, too short for a screen drawn ten times a second to ever show a pause. Every frame saved from Screen on the target matched our host replay pixel for pixel, 11 of 11. Switching the console on made no difference to missed ticks that we could measure on this emulator.

What the target taught us

The first runs on QNX did not all pass, and each failure led to a real improvement rather than a looser test:

  • One early run counted only about 850 ticks a second, and we first credited a call asking QNX for a 0.5 ms system tick. Testing that call on its own showed QNX 8.0 in QEMU keeps a fixed 1 ms tick and refuses the change, so the slow run was the virtual machine. Every run since counts about 1,000 ticks a second, and the controller now reads the tick instead of assuming it.
  • A paused controller let a stiff chest reach 823 N. The motor driver now has its own force limit, so the hard limit holds even when software is late.
  • Road motion compensation moved from the controller into the driver, the way real motion systems split the work, so a late controller cannot make the depth wrong.
  • After a pause the controller replays the ticks it missed, using the buffered motion samples, so its clocks stay in step with real time.
  • A start up bug in the supervisor, and a test that watched the wall clock instead of the controller's clock, were fixed.
  • After a pause the controller replayed missed ticks with the newest sample, so the whole movement during the pause looked like it happened in 1 ms. The force guard tripped early and strokes came up short (43 to 50 mm). Speed is now measured over real hardware sample time, and two host scenarios that stall the controller guard against this coming back.
  • When the whole virtual machine froze, the controller could wake before the hardware had its turn and call the sensors silent. Silence is now counted only over time the controller was awake to see it. A real sensor loss is still caught within the timeout.
  • The stiff chest fault was injected in the middle of a push, which no controller can stop. It now takes effect at full recoil, the way a different patient would.
  • The CPU storm test used to compare missed ticks with and without the storm. On a virtual machine that number measures the host: one run missed more ticks with the storm, the next missed fewer. The test now judges what the patient gets during the storm: compressions on rate, every stroke 5 to 6 cm, no rule broken, no fault. Missed ticks are still printed.
  • The test crew pressed once, from a status read a second old. It now behaves like a real crew and presses whenever the device asks.

At real hardware timings

We also ran the suite at the timings a real board will use: a 5 ms sensor timeout and a 20 ms hardware watchdog. Here QEMU runs inside WSL2, which is itself a virtual machine on Windows, and its virtual CPUs can freeze for longer than 5 ms. The first strict run passed 5 of 11 cases. Every failure was the controller correctly calling the sensors silent and retracting to safety. Two idle threads at the lowest priority keep the virtual CPUs awake without touching anything else, and with them 9 of 11 pass, including the full shock and return of circulation. Transport and the malicious advisor case still trip the 5 ms timeout. We think only real hardware can settle these numbers, and both runs are published in full.
